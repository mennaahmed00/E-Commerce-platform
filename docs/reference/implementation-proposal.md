## 3. Global Conventions

These apply to every NestJS service unless a section below says otherwise.

- **IDs:** UUID v4 everywhere, generated by Postgres (`gen_random_uuid()`, via the `pgcrypto` extension) or Mongo ObjectId for the Messaging service.
- **Timestamps:** `TIMESTAMPTZ` in Postgres, serialized as ISO 8601 strings in JSON (`createdAt`, `updatedAt`).
- **Money:** always integer cents (`priceCents`, `totalCents`), never floats. Currency as a separate ISO 4217 string field (`currency`, default `"EGP"`).
- **Casing:** `snake_case` in the database, `camelCase` in JSON/API payloads. With raw SQL there's no ORM layer doing this translation automatically — every repository function must explicitly map row keys to camelCase on the way out (a small `toCamelCase` row-mapper helper in `packages/shared-http` is enough; don't let snake_case leak into API responses, and don't rely on each service reinventing this mapper).
- **Pagination:** limit/offset on every list endpoint. Query params `?limit=20&offset=0`, `limit` default 20 / max 100. Response shape:
  ```json
  { "data": [...], "total": 143, "limit": 20, "offset": 0 }
  ```
- **Error shape** (every 4xx/5xx from every service):
  ```json
  { "statusCode": 400, "error": "Bad Request", "message": "email must be a valid email", "path": "/auth/register", "timestamp": "2026-09-14T10:00:00.000Z" }
  ```
  Use a shared NestJS exception filter in `packages/shared-http` so this is identical across services.
- **Health check:** every service exposes `GET /health` returning `{ "status": "ok" }`, no auth required. Used by Docker Compose healthchecks.
- **Every list/detail endpoint that touches tenant-scoped data must go through the tenant-context middleware described in §5 — no exceptions, no "just this one query without it."**

## 4. Auth Model — Two Separate Token Types

### 4.1 External auth token (merchant owner / employee / platform admin)

Issued by **Identity & Tenancy Service** at `/auth/login`. JWT (HS256), secret in env var `AUTH_JWT_SECRET` (shared only between Identity Service and Gateway — no other service ever sees this token).

Access token claims:
```json
{
  "sub": "user-uuid",
  "tenantId": "tenant-uuid | null",
  "role": "platform_admin | owner | employee",
  "permissions": ["products.write", "orders.write", "integrations.payment.manage"],
  "iat": 1234567890,
  "exp": 1234571490
}
```
- Access token TTL: 15 minutes.
- Refresh token: opaque random string, stored hashed in `identity_db.refresh_tokens`, TTL 30 days, rotated on every use.
- `tenantId` is `null` only for `platform_admin` role.
- `permissions` is populated only for `role: employee` (owners implicitly have all permissions — don't populate the array for owners, the Gateway treats `role: owner` as all-permissions).

### 4.2 Internal service token (Gateway → downstream services)

The Gateway is the **only** service that ever sees the external `AUTH_JWT_SECRET`. On every incoming request, after verifying the external JWT, the Gateway mints a short-lived internal JWT and forwards it — downstream services never see or verify the external token.

- Secret: `INTERNAL_JWT_SECRET` (shared across Gateway + all NestJS services, different from `AUTH_JWT_SECRET`).
- TTL: 60 seconds (minted fresh per request, not reused).
- Sent as header: `Authorization: Internal <token>`.
- Claims: `{ "tenantId": "...", "userId": "...", "role": "...", "permissions": [...], "iat": ..., "exp": ... }`.
- Every NestJS service (except Identity's public `/auth/*` routes) uses `InternalAuthGuard` from `packages/shared-auth` to verify this token and populate `request.tenantContext`. A service must **reject** any request that doesn't carry a valid internal token — this is what stops someone from bypassing the Gateway and hitting a service directly with a forged tenant ID.
- Platform-admin requests carry `tenantId: null` — services that get a null tenantId and a non-platform_admin role must reject with 403.

### 4.3 Customer auth (storefront, optional accounts)

Customer accounts are **per-store** and live in the Commerce service (`customer_accounts` table), not Identity. Two paths:
- **Guest checkout:** no token at all. Phone number is captured directly on the checkout DTO (`customerPhone`, required, E.164 format, validated).
- **Logged-in customer:** Commerce service issues its own lightweight JWT on `/storefront/:tenantId/auth/login`, secret `CUSTOMER_JWT_SECRET`, TTL 7 days, claims `{ sub: customerAccountId, tenantId }`. This token is only ever checked by Commerce service itself — Gateway passes it through unmodified for storefront routes, it does not get converted into an internal token.

## 5. Tenancy Implementation (Row-Level Security)

Applies to every Postgres-backed service (Identity, Commerce, Storefront, Integrations). Not applicable to Messaging (Mongo, filter by `tenantId` field in every query, no RLS mechanism there — same discipline, different enforcement layer).

### 5.1 Migration pattern (every tenant-scoped table)

```sql
ALTER TABLE products ENABLE ROW LEVEL SECURITY;
ALTER TABLE products FORCE ROW LEVEL SECURITY; -- applies even to the table owner
CREATE POLICY tenant_isolation ON products
  USING (tenant_id = current_setting('app.tenant_id', true)::uuid);
```
Run this for every table that has a `tenant_id` column. Tables with no `tenant_id` (the `tenants` table itself, and later the Trust & Risk service's tables) get no RLS policy at all.

### 5.2 Setting the session variable (NestJS + raw `pg`)

`SET LOCAL` is transaction-scoped in Postgres, so every tenant-scoped request must check out a single client from the pool and run its `SET LOCAL` + queries inside one transaction — never let the tenant-context query and the data query end up on two different pooled connections.

```typescript
// packages/shared-auth/tenant-context.ts
import { Pool, PoolClient } from 'pg';

const UUID_RE = /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i;

async function withTenantContext<T>(pool: Pool, tenantId: string, fn: (client: PoolClient) => Promise<T>): Promise<T> {
  if (!UUID_RE.test(tenantId)) {
    throw new Error('Invalid tenantId'); // never string-interpolate an unvalidated value into SQL, even for SET LOCAL
  }
  const client = await pool.connect();
  try {
    await client.query('BEGIN');
    // SET LOCAL doesn't accept query parameters ($1) — this is the one place a value gets
    // interpolated directly, which is exactly why the UUID regex check above is not optional.
    await client.query(`SET LOCAL app.tenant_id = '${tenantId}'`);
    const result = await fn(client);
    await client.query('COMMIT');
    return result;
  } catch (err) {
    await client.query('ROLLBACK');
    throw err;
  } finally {
    client.release();
  }
}
```
Every other query inside `fn` must use parameterized queries (`client.query('SELECT * FROM products WHERE id = $1', [id])`) — the UUID-regex guard above is specifically for the `tenant_id` value because `SET LOCAL` is the one query in this whole codebase that can't be parameterized. Don't relax that check anywhere.

Wire `withTenantContext` as a NestJS interceptor/request-scoped provider that reads `request.tenantContext.tenantId` (set by `InternalAuthGuard`, §4.2) and hands controllers a client that's already inside the right transaction — don't make every controller call `withTenantContext` manually; that's exactly the kind of "forget it once" bug this pattern exists to prevent. Since there's no ORM enforcing this, treat "every tenant-scoped repository method takes a `client: PoolClient`, never a bare `pool`" as a hard lint-level rule, not a convention people remember.

### 5.3 Platform-admin bypass

Platform-admin-only endpoints (tenant list, tenant status changes — Identity Service only) connect using a separate Postgres role with `BYPASSRLS`, via a second `Pool` instance (`adminPool`) configured with that role's credentials, used only in the handful of controllers gated behind `role: platform_admin`. Never use this pool for anything else, and never run it inside `withTenantContext` — it doesn't need the session variable and shouldn't be mixed with the tenant-scoped path.

**Checkout flow (`POST /storefront/:tenantId/checkout`)**
Request: `{ cartId, customerPhone, shippingAddress, paymentMethod: "cod" | "card" }`
1. Load cart + items within `withTenantContext`, validate all variants still have sufficient `stock_qty`. If not → `409 Conflict` with the specific out-of-stock variant IDs.
2. Create `order` + `order_items` (snapshotting price/title), decrement `stock_qty` on each variant, in one transaction on the same `client` from `withTenantContext` — do the stock-decrement as `UPDATE product_variants SET stock_qty = stock_qty - $1 WHERE id = $2 AND stock_qty >= $1` and check `rowCount === 0` to catch a race against another concurrent checkout, rather than reading stock then writing it back (a read-then-write here is a classic double-sell bug under concurrency).
3. If `paymentMethod: "card"` → call Integrations Service internal endpoint `POST /internal/payment/charge` (see §6.4). If it returns failure → roll back the stock decrement and order creation, return `402 Payment Required`.
4. If `paymentMethod: "cod"` → skip step 3, order goes straight to `status: confirmed`, `payment_status: unpaid`.
5. Mark cart `status: converted`.
6. Return the created order.

No trust-score branching at MVP — that's the Grad 2 flow described in `system-architecture.md` §7. `paymentMethod` is a raw customer choice for now, not risk-tier-driven.

No other service calls the AI Service synchronously at MVP except the Gateway proxying `/api/ai/chat` for a demo-able "chat widget" if the team wants one — entirely optional, not required for MVP acceptance.

### 6.7 API Gateway

No database. Responsibilities, in order, per request:

1. **Tenant resolution:** parse `Host` header. If it matches `*.platform.local` (dev) or the configured base domain, extract subdomain → look up `tenantId` via a cached call to Identity Service (`GET /tenants/by-subdomain/:subdomain`, add this internal endpoint to Identity). If it's a custom domain, look up via `GET /tenants/by-domain/:domain`. Cache the subdomain/domain → tenantId mapping in Redis, TTL 5 minutes.
2. **JWT verification:** for routes under `/api/` that aren't in the public allowlist (see below), verify the `Authorization: Bearer <token>` external JWT using `AUTH_JWT_SECRET`. Reject with 401 if missing/invalid/expired.
3. **Mint internal token:** build the internal JWT (§4.2) from the verified claims + resolved tenantId, attach as `Authorization: Internal <token>` on the proxied request.
4. **Route:** proxy to the correct downstream service based on path prefix (table below). Use `packages/shared-http`'s typed client, not raw `fetch` scattered through the codebase.

**Public routes (no external JWT required)** — Gateway still resolves tenant, but skips step 2:
- `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/refresh`
- `GET /api/storefront/:tenantId/*` (all storefront-facing Commerce/Storefront/Messaging routes)
- `POST /api/storefront/:tenantId/checkout`, `/cart`, `/messages`

**Path prefix → service routing table**
| Prefix | Target service |
|---|---|
| `/api/auth`, `/api/tenants`, `/api/employees`, `/api/permissions` | Identity (3001) |
| `/api/products`, `/api/categories`, `/api/variants`, `/api/orders`, `/api/storefront/:tenantId/products`, `/api/storefront/:tenantId/cart`, `/api/storefront/:tenantId/checkout` | Commerce (3002) |
| `/api/themes`, `/api/storefront/:tenantId/theme` | Storefront (3003) |
| `/api/payment`, `/api/shipping` (config endpoints only — internal endpoints are never exposed through the Gateway) | Integrations (3004) |
| `/api/conversations`, `/api/storefront/:tenantId/messages` | Messaging (3005) |
| `/api/ai` | AI Service (8000) |

**Internal-only endpoints (prefixed `/internal/` on each service) must never be reachable through the Gateway's routing table** — enforce this with an explicit denylist check in the Gateway's router, not just "we didn't add a route for it."

## 7. Frontend (`/apps/web`, Next.js)

- Single Next.js App Router project serving two experiences via `middleware.ts`:
  - Requests to `app.platform.local` (or the platform's own domain) → merchant dashboard (`/dashboard/*` route group), requires the external JWT (stored in an httpOnly cookie after login).
  - Requests to any other resolved subdomain/custom domain → storefront (`/store/*` route group), reads the tenant from the `Host` header the same way the Gateway does.
- All API calls go through the Gateway (`NEXT_PUBLIC_API_URL`), never directly to a backend service.
- Theme rendering: fetch `GET /api/storefront/:tenantId/theme`, feed the returned `puck_data` into Puck's `<Render>` component. Do not build a custom renderer.
- Out of scope for MVP frontend: raw-code theme editing UI, AI chat widget UI (backend stub exists but no UI requirement), employee permission management UI beyond a basic checkbox list, mobile app (separate React Native project, not part of this repo at MVP).

## 10. Suggested Build Order

Sequenced so each step is independently testable before the next depends on it:

1. Monorepo scaffold (`pnpm-workspace.yaml`, `packages/shared-types`, `packages/shared-auth` — including the `withTenantContext` helper and row-mapper from §5/§3, since every service depends on getting this right identically — `packages/shared-http`), Docker Compose with just `postgres`, `mongo`, `redis` running.
2. **Identity & Tenancy Service** end-to-end (register, login, refresh, tenant/employee CRUD) — everything else depends on auth existing.
3. **Gateway**, wired only to Identity at first (tenant resolution + JWT verify + internal-token minting) — prove the auth flow works through the Gateway before adding more services behind it.
4. **Commerce Service**: products/categories/variants CRUD first, then cart, then checkout with `paymentMethod: "cod"` only (no Integrations dependency yet) — get a full guest-checkout-to-COD-order flow working before touching payments.
5. **Integrations Service** with a sandbox payment adapter; wire Commerce's `paymentMethod: "card"` path to it.
6. **Storefront/Theme Service** + seed default themes + wire Identity's `/auth/register` to call its seed endpoint.
7. **Messaging Service** (basic message box, storefront-initiated conversations only).
8. **AI Service** stub (can be done in parallel with any of the above by the 2 AI-focused team members — it has no real dependency on the others at MVP).
9. **Frontend** (`/apps/web`) — dashboard first (auth, product management), then storefront (browse, cart, checkout, theme rendering), then the basic message box UI.

## 11. Explicit Out of Scope for This Spec (do not build)

- Trust & Risk Service and any risk-tier/prepayment logic — `payment_status` only ever becomes `unpaid`/`paid` at MVP, no `partial` state.
- Event bus (RabbitMQ) and anything async — every inter-service call in this spec is synchronous REST.
- Notification Service, WhatsApp/IVR order confirmation, any AI-driven auto-reply in Messaging.
- Meta integration (ads, unified inbox beyond the storefront's own message box).
- Multiple payment/shipping providers — exactly one of each, fixed by env var, no provider-selection UI.
- Raw-code theme editing, Monaco editor, custom theme code files — Puck JSON only.
- Real AI models of any kind (RAG chatbot, RFM/churn/sentiment models, product description generation, visual search, virtual try-on, Jarvis assistant, media buying, buying agent) — AI Service is a stub per §6.6.
- Bulk product upload via Excel, low-stock alert notifications (the `low_stock_threshold` column exists in the schema so Grad 2 doesn't need a migration, but nothing reads it yet).
- Returns/exchange authorization flow.
- Instapay-specific confirmation flow (generic `payment_status: paid` covers it for MVP demo purposes).
- Mobile application.
- Analytics/reporting service, ads-data dashboards, financial calculator — dashboards at MVP are direct reads against Commerce/Identity, nothing pre-aggregated.
- Kubernetes or any orchestration beyond Docker Compose.
- Meilisearch wiring — container exists, unused.
